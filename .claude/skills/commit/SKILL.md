# Commit

변경사항을 분석하여 컨벤션에 맞는 커밋을 만드는 스킬입니다. 사용자 승인 없이는 절대 커밋하지 않습니다.

## 절차

### 1. 변경사항 분석

다음을 병렬로 실행합니다.

- `git status` (untracked 파일 포함)
- `git diff` (unstaged)와 `git diff --staged` (staged)
- `git log --oneline -10` (기존 메시지 스타일 확인)

git 저장소가 아니거나 변경사항이 없으면 그 사실을 알리고 종료합니다.

### 2. 논리적 단위로 분류

- 하나의 커밋은 하나의 목적만 담습니다. 기능 추가, 버그 수정, 리팩터링, 설정 변경이 섞여 있으면 나눕니다.
- 같은 목적의 코드·스타일·테스트는 한 커밋으로 묶습니다.
- 파일 일부만 다른 단위에 속하면 `git add -p` 대신 사용자에게 분리 여부를 묻습니다 (interactive 플래그는 이 환경에서 쓸 수 없습니다).
- `.env`, 키·토큰이 들어간 파일, `node_modules`, 빌드 산출물(`dist`)은 커밋 대상에서 제외하고 발견하면 사용자에게 알립니다. 의심스러운 파일은 내용을 확인합니다.

### 3. 커밋 메시지 작성

형식: `타입: 요약`

| 타입 | 용도 |
| --- | --- |
| feat | 새 기능 |
| fix | 버그 수정 |
| refactor | 동작 변경 없는 구조 개선 |
| chore | 설정, 의존성, 빌드, 문서 등 기타 |

규칙:

- 요약은 한국어, 50자 안팎, 마침표 없이 "무엇을 했는지"를 씁니다. 예: `feat: 프롬프트 예시 칩 추가`
- 이유가 자명하지 않으면 빈 줄 뒤 본문에 "왜"를 한두 줄로 적습니다.
- 시스템 안내에 커밋 속성(attribution) 줄이 있으면 메시지 끝에 그대로 덧붙입니다.

### 4. 사용자 승인

커밋 전에 아래를 보여주고 승인을 받습니다 (AskUserQuestion 사용 가능).

- 커밋별 대상 파일 목록
- 커밋별 메시지 전문

승인, 수정 요청, 취소 중 하나를 받습니다. 수정 요청이면 반영 후 다시 확인합니다.

### 5. 커밋 실행

승인된 커밋마다 순서대로:

1. `git add <파일들>` — 파일을 명시합니다. `git add -A`와 `git add .`는 쓰지 않습니다.
2. `git commit -m "$(cat <<'EOF' ... EOF)"` — HEREDOC으로 메시지를 전달합니다.
3. 모두 끝나면 `git status`와 `git log --oneline`으로 결과를 확인해 요약합니다.

pre-commit hook이 실패하면 원인을 고쳐 새 커밋을 만듭니다. `--no-verify`와 `--amend`는 사용자가 요청하지 않는 한 쓰지 않습니다.

## 하지 말 것

- 승인 전에 `git add`나 `git commit` 실행
- `git push` (사용자가 따로 요청할 때만)
- 여러 목적의 변경을 한 커밋에 몰아넣기
- 영어 메시지 (사용자가 요청하지 않는 한)
