# TDD Rule

**이 규칙은 Rigid — 상황에 맞게 변형하지 마라.** 단계를 건너뛰거나 순서를 바꾸지 않는다.

## 1. 적용 기준

### 반드시 TDD를 적용한다

- **비즈니스 로직**
- **API** (핸들러, 요청/응답 처리, 에러 매핑)
- **유틸 함수** (순수 함수, 변환, 파싱)
- **버그 수정** (먼저 버그를 재현하는 실패 테스트를 작성한다)

### TDD가 불필요하다

- **타입 정의** (`interface`, `type`만 있는 파일)
- **설정 파일** (`vite.config.ts`, `tsconfig.json`, `eslint.config.js` 등)
- **순수 UI** (동작 없이 마크업과 스타일만 바꾸는 변경)
- **SQL** (스키마, 마이그레이션)

경계가 모호하면 **적용하는 쪽**을 택한다. 순수 UI라도 클릭, 입력, 조건부 렌더링 같은 동작이 있으면 TDD 대상이다.

## 2. RED - GREEN - REFACTOR

### RED: 실패하는 테스트 작성

1. **하나의 동작 = 하나의 테스트.** 한 테스트에 여러 동작을 섞지 않는다.
2. 테스트 이름은 기대하는 동작을 서술한다.
3. **반드시 실행해서 실패를 확인한다.** 실행하지 않은 테스트는 RED가 아니다.
4. **실패 이유가 "기능 미구현"이어야 한다.** 다음은 RED가 아니므로 테스트부터 고친다.
   - 문법 오류, import 오류, 오타
   - 테스트 설정 문제
   - 처음부터 통과하는 테스트

### GREEN: 최소한의 코드

1. 테스트를 통과시키는 **최소한의 코드만** 작성한다.
2. **YAGNI.** 아직 테스트가 요구하지 않는 분기, 옵션, 추상화를 넣지 않는다.
3. **신규 테스트와 기존 테스트가 모두 통과**하는지 전체를 실행해 확인한다.
4. 하드코딩으로 통과시켜도 된다. 다음 RED가 일반화를 강제한다.

### REFACTOR: 정리

1. **중복 제거, 이름 개선, 헬퍼 추출**만 한다.
2. **모든 테스트가 green인 상태를 유지한다.** 변경할 때마다 실행한다.
3. **새 동작을 추가하지 않는다.** 새 동작이 필요하면 다음 RED에서 한다.

### 반복

REFACTOR가 끝나면 **다음 동작의 RED로 돌아간다.** 요구사항의 모든 동작을 다룰 때까지 반복한다.

## 3. 삭제 강제 규칙

테스트 전에 프로덕션 코드를 먼저 작성했다면:

1. **그 코드를 삭제한다.**
2. **RED부터 다시 시작한다.**

**"참고용"으로 남기는 것도 금지.** 주석 처리, 임시 파일, 다른 브랜치에 보관, 복사해 두고 보면서 다시 쓰기 모두 포함한다. 남겨 둔 코드는 테스트를 그 코드에 끼워 맞추게 만든다.

## 4. 변명 차단표

| 변명 | 반론 |
| --- | --- |
| 너무 단순해서 테스트 불필요 | 단순한 코드는 테스트도 단순하다. 비용이 거의 없고, 나중에 단순하지 않게 바뀔 때 회귀를 막는다. |
| 나중에 테스트를 추가하겠다 | 나중에 쓴 테스트는 구현을 보고 쓰므로 현재 동작을 그대로 통과시킨다. 버그를 못 잡고, 실제로는 쓰이지 않는 경우가 많다. |
| 시간이 없다 | 디버깅과 수동 확인이 테스트 작성보다 오래 걸린다. 급할수록 실패를 빨리 알려주는 테스트가 필요하다. |
| 삭제하면 낭비다 | 이미 쓴 시간은 매몰 비용이다. 검증 안 된 코드를 유지하는 비용이 다시 쓰는 비용보다 크다. 다시 쓰면 더 빠르다. |
| 프로토타입이다 | 프로토타입은 자주 그대로 제품이 된다. 버릴 코드라면 테스트도 같이 버리면 되므로 쓰지 않을 이유가 아니다. |

## 5. 프로젝트별 규칙 우선

- 프로젝트의 `CLAUDE.md` 또는 `AGENTS.md`에 TDD 규칙이 있으면 **그 규칙이 이 파일보다 우선한다.**
- **이 파일은 기본값(fallback)이다.** 프로젝트 규칙이 다루지 않는 부분에만 적용한다.
- 충돌하면 프로젝트 규칙을 따르고, 이 파일의 해당 항목은 무시한다.
